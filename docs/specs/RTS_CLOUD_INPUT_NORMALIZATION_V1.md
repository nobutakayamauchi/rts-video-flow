# RTS Cloud Input Normalization v1

Status: APPROVED FOR IMPLEMENTATION  
Scope: governed Cloud Run render preparation  
Applies to: `prepare-project` staging before Security Gate, GCS upload, approval, and dispatch

## 1. Purpose

Cloud render inputs must be converted into a predictable, minimal media shape before they are inspected or uploaded.

The normalizer exists to remove container tracks that are not required to render the Vlog, while preserving the original source material unchanged.

This specification does **not** relax the Security Gate. It defines a canonical input form that must pass the existing fail-closed gate.

## 2. Source protection

- Original project media is read-only.
- Original files, project plans, narration assets, and edit settings must not be modified.
- Normalization operates only on a run-scoped staging copy.
- A failure must not replace, rename, truncate, or delete the original file.
- Staging artifacts may be deleted after the handoff completes or fails according to the retention policy.

## 3. Canonical stream contract

Each normalized video input must contain:

- exactly one video stream: the first renderable video stream;
- zero or one audio stream: the first required audio stream when present;
- zero data streams;
- zero subtitle streams;
- zero attachment streams;
- zero other unknown or unsupported streams.

Tracks used only for device metadata, timecode, location, motion, depth, auxiliary capture information, or container-specific data are not part of the Cloud Render input contract.

## 4. Normalization rules

For each staged source:

1. Probe the copied source with `ffprobe`.
2. If the source already satisfies the canonical stream contract, it may be copied unchanged into the canonical staging area.
3. If removable auxiliary streams are present, create a normalized container containing only:
   - `0:v:0`;
   - `0:a:0?`.
4. Do not map data, subtitle, attachment, or unknown streams.
5. Prefer stream copy/remux so that video and audio are not re-encoded.
6. Preserve only metadata required for correct playback. Device-specific auxiliary tracks are not preserved.
7. Use an internal ASCII filename generated by the staging process.
8. Probe the normalized output again before Security Gate inspection.

Reference command shape:

```bash
ffmpeg -v error -y \
  -i input.mov \
  -map 0:v:0 \
  -map 0:a:0? \
  -c copy \
  -map_metadata -1 \
  -movflags +faststart \
  normalized.mp4
```

The exact container may vary when stream-copy compatibility requires it, but the resulting file must satisfy the canonical stream contract.

## 5. Re-encoding policy

- Stream-copy/remux is the default and preferred path.
- The normalizer must not silently re-encode video or audio.
- If remux cannot produce a valid canonical file, the run must fail closed with an actionable error.
- A future re-encoding fallback requires a separate approved specification, explicit resource limits, and cost accounting.

## 6. Security Gate order

The required order is:

```text
original source
  -> run-scoped staging copy
  -> stream normalization
  -> post-normalization ffprobe
  -> Security Gate
  -> cost estimate
  -> GCS upload
  -> approval
  -> dispatch
```

Security Gate must inspect and hash the normalized file that will actually be uploaded. Hashes, file sizes, stream counts, and the security fingerprint must therefore bind to the canonical staged input, not to the untouched original source.

## 7. Security Gate acceptance

After normalization, a video file is accepted only when:

```text
video      = 1
audio      = 0..1
data       = 0
subtitle   = 0
attachment = 0
unknown    = 0
```

Existing limits for file size, duration, resolution, frame rate, filename safety, regular-file status, and symlink rejection remain in force.

The numeric `MAX_STREAMS` guard may remain as defense in depth, but it must not be increased merely to admit auxiliary iPhone or container data tracks.

## 8. Logging and audit record

Each normalization attempt must record enough information to explain what changed without exposing private media content.

Minimum record:

```text
source path or project-relative identifier
source stream summary by codec type
normalized stream summary by codec type
normalization method: passthrough or remux
output path
elapsed time
result: PASS or REJECT
error summary when rejected
```

Example:

```text
Source: video=1 audio=1 data=5 subtitle=0
Normalized: video=1 audio=1 data=0 subtitle=0
Method: remux
Result: PASS
```

## 9. Failure behaviour

The normalizer must reject the input and stop before upload when any of the following applies:

- no usable video stream exists;
- more than one video stream remains after normalization;
- the selected stream cannot be copied into a supported canonical container;
- `ffprobe` or `ffmpeg` times out or fails;
- the normalized output is empty, missing, a symlink, or outside the run staging directory;
- post-normalization probing still reports data, subtitle, attachment, or unknown streams;
- post-normalization Security Gate rejects the file.

Failure must leave the handoff unapproved and must not start Cloud Run.

## 10. Current motivating case

Some iPhone `.mov` files contain one video stream, one audio stream, and four or five auxiliary data streams. These tracks caused `stream count outside security limit` even though the visible media itself was valid.

Under this specification, the source file remains untouched. The Cloud input copy is remuxed to one video stream plus the first audio stream, auxiliary data tracks are removed, and the normalized file is then inspected by the Security Gate.

## 11. Non-goals

This version does not:

- merge multiple audio tracks;
- choose alternate camera angles;
- burn subtitles into video;
- transcode unsupported codecs;
- alter timeline ordering;
- change narration or source-audio selection rules;
- relax approval, cost, bucket, task-count, timeout, or single-use controls.

## 12. Implementation acceptance criteria

Implementation is complete when automated tests demonstrate that:

1. original files are unchanged;
2. a normal two-stream file passes through safely;
3. an iPhone-style file with auxiliary data tracks becomes exactly one video plus zero or one audio stream;
4. data, subtitle, attachment, and unknown streams are absent from the normalized output;
5. normalization uses stream copy and does not silently re-encode;
6. Security Gate hashes the normalized output;
7. normalization failure prevents GCS upload and handoff creation;
8. no Cloud Run job is started by normalization itself.
